## 七、经验教训：仓库拉取

本 session 尝试了 6 种方式拉取仓库，结论：

| # | 方式 | 耗时 | 结果 |
|---|------|------|------|
| 1 | SSH clone | ~2s | ❌ 密钥未配置时失败 |
| 2 | HTTPS clone（完整） | ~10min | ❌ GnuTLS 超时 |
| 3 | HTTPS clone（`--depth 1`） | ~10min | ❌ 同上 |
| 4 | HTTPS + `http.postBuffer` | ~90s | ❌ 同上 |
| 5 | curl 直连下载 tarball | ~90s | ❌ 半断（1.5MB/3MB） |
| 6 | **ghfast.top 代理 tarball** | **~2s** | ✅ 成功 |

**核心结论：瓶颈是这台机器到 GitHub 的网络链路不稳定（GnuTLS -110），不是协议选择。SSH 和 HTTPS 都走 GitHub 直连，都会卡。ghfast.top 走国内 CDN 中转，绕过了直连瓶颈。**

**下次推荐方案：**
1. 首选：`ghfast.top` 代理下载 tarball（最快，2秒，但需注意仓库大小限制）
2. 备选：配置 SSH 密钥后用 SSH clone（密钥交换后加密开销低于 TLS）
3. 保底：GitHub API 按目录分批拉取（避免一次性传大包）

**注意：** tarball 方式没有 .git 历史，需要手动 `git init` + `git remote add` + force push。如果需要保留 commit 历史，仍需走 git clone。
